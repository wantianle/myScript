# SPEC

## Purpose

构建一套运行在 Orin 域控台架上的每日开环冒烟测试工具，面向开发和测试同学，自动完成版本安装、模块切换、原始传感器数据回灌与重录制，生成新的验证数据包，作为后续算法验证的输入基线。

第一版聚焦打通最小主流程：从人工维护的数据集清单出发，完成版本更新、环境准备、数据回灌、录制和执行记录；暂不纳入算法自动验证、HTML 报告和 NAS 自动回传。设计上允许后续向服务化架构演进，但第一版不以服务化落地为目标。

## User Scenarios

### Scenario 1: 每日一键冒烟
测试同学选择一个或多个已维护的数据集，并提供当日需要验证的版本号，一键执行完整流程，最终获得新的验证数据包、版本信息和执行日志。

### Scenario 2: 问题排查与分步调试

开发或测试同学在流程某一步失败后，使用 debug 模式按步骤执行，定位失败发生在版本安装、模块切换、数据准备、回灌还是录制阶段。

### Scenario 3: 为后续算法验证准备标准化输入
操作者针对安全接管类数据批量生成新的验证数据包，并记录数据集 ID、版本信息、命令和输出路径，供后续算法验证流程复用。

## Functional Requirements

1. **数据集清单输入**
   - 系统必须支持读取人工维护的数据集清单。
   - 清单至少包含：问题描述、飞书单链接、飞书单 ID（作为数据 ID）、原始数据路径。

2. **版本安装**
   - 系统必须支持接收用户提供的版本参数，用于执行每日版本更新。
   - 第一版应优先依赖 `md-tool` 执行安装流程，而不是直接编排 `vmc`。
   - 系统必须支持在 soc1 上执行 `md install <version>` 完成版本安装。
   - 所有目标版本安装完成后，系统必须执行 `md start` 启动 `mdrive` 服务。
   - 系统必须记录安装命令、执行结果以及必要的版本信息摘要。

3. **数据准备**
   - 系统必须支持将数据从数据集清单中给定的源路径拷贝到本地 `/mdrive_data/base_test/` 下的工作目录。
   - 第一版默认使用 `rsync` 做本地化准备。
   - 系统必须记录源路径、本地路径和拷贝结果。

4. **台架模块切换**
   - 系统必须支持在双 Orin 环境下分别处理 soc1 和 soc2 的模块控制。
   - 系统必须支持通过 SSH 访问对应目标环境，并执行模块停启命令。
   - 当前双 soc 间通信地址应基于：
     - soc1: `nvidia@192.168.10.2`
     - soc2: `nvidia@192.168.10.3`
   - 系统必须支持关闭以下模块：
     - soc1: `Camera`, `Canbus`
     - soc2: `Camera`, `Driver-GNSS`, `Driver-LiDAR`, `Driver-NTRIP`
   - 系统必须支持启动以下 debug 模块：
     - soc2: `Debug_Camera-Decode`, `Debug_Driver-LiDAR`
   - 系统必须在进入回灌前确认所需模块切换步骤已完成，并记录执行结果。

5. **数据回灌**
   - 系统必须支持使用 `mkit play` 回灌原始传感器数据。
   - 回灌命令必须覆盖当前约定的 topic 集合。
   - 系统必须支持以文件输入方式执行回灌，并支持通配符匹配目标文件。
   - 第一版不得使用 `-l` 循环播放，避免录制到重复数据。
   - 系统必须支持针对单个数据包执行一次完整回灌。

6. **录制控制**
   - 系统第一版应优先直接使用底层 `mkit record` 命令进行重录制，而不是依赖 `supervisorctl start Recorder` 封装。
   - 录制命令应基于域控已有环境变量，并在执行前显式 `source ${MDRIVE_ROOT_DIR}/mdrive/setup.sh`。
   - 录制输出路径必须可由工具显式控制。
   - 系统必须协调“回灌进程”和“录制进程”的开始与结束。
   - 当无法做到严格同时开始和结束时，系统应优先保证“不录到循环数据”，允许录制略短。
   - 系统必须记录新生成 mcap 的输出路径。

7. **执行模式**
   - 系统必须支持一键全流程执行模式。
   - 系统必须支持 debug 模式，使操作者能够分步骤执行并排查问题。

8. **日志与结果记录**
   - 系统必须对每个步骤记录执行状态、关键命令、成功/失败判定和必要日志。
   - 系统必须记录版本信息。
   - 系统在录制阶段应保留 `vmc list` 或等价版本信息采集结果，供追溯使用。
   - 系统必须记录输出文件的基础信息，至少支持对生成 mcap 执行 `mkit info`。
   - 系统必须记录最终产物路径，例如 `/mdrive_data/bag/record_<日期>/record.0000x.*.mcap`。

9. **失败处理**
   - 任一步骤失败时，系统必须将整次任务判定为失败并停止后续关键流程。
   - 系统必须明确指出失败步骤和对应日志位置。

## Non-functional Requirements

1. **运行环境约束**
   - 运行环境为 Orin 域控台架，Ubuntu 20.04，Python 3.8。
   - 环境无网络，依赖本机已有工具与共享挂载目录。
   - `/media/nas` 与 `/mdrive_data` 为关键数据路径。
   - 数据源路径由人工维护的数据集文件提供，而不是由工具推断。
   - 本地数据下载根目录固定为 `/mdrive_data/base_test/`。
   - 工具执行前应校验 `/media/nas` 已正确挂载。

2. **可靠性**
   - 流程必须以失败即停止为默认策略，避免在异常状态下继续执行。
   - 录制策略必须优先避免重复数据进入结果包。
   - 第一版默认不复用历史本地化数据目录，避免运行结果混淆。

3. **可追溯性**
   - 每次执行必须可追溯到数据集 ID、输入路径、版本信息、执行命令、输出路径和步骤结果。

4. **可维护性**
   - 第一版实现必须保持流程步骤清晰、可分解，便于后续增加 HTML 报告、NAS 回传和算法验证能力。
   - 设计上应保留向服务化架构演进的余地，但 MVP 不引入服务化部署复杂度。

5. **可操作性**
   - 工具必须同时适配“日常一键运行”和“开发排障”两类使用方式。

## Out of Scope

1. 自动数据采集、自动筛选或自动构建数据集。
2. 算法自动验证、指标计算和效果评估闭环。
3. HTML 报告生成。
4. 录制结果自动上传 NAS。
5. 复杂远程控制、分布式调度或多机统一编排平台。
6. 底软模块本身的开发、修复或替代实现。
7. Web UI、权限系统、账号体系或在线服务化部署。
