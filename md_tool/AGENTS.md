# 仓库指南

## 项目结构与模块组织
该仓库是一个基于 Bash 的运维工具集。`md.sh` 是主入口脚本，负责设备检查、服务控制、日志导出和包管理。`deploy.sh` 用于将 `md.sh` 和 `bin/` 中的 `.deb` 包部署到远端目标。`ssh.sh` 用于初始化免密登录和本地 `~/.ssh/config` 配置。`bin/` 存放随仓库分发的依赖包。`md_go/` 是 Go 重构实验工程（骨架阶段，业务未迁移）。`mdrive服务管理工具.md` 是工具的用户手册。注：适配 mdrive2 的旧版工具集已拆出到仓库根目录的 `md_old/` 独立目录，不属本目录源码。

## 构建、测试与开发命令
这些脚本目前未统一设置可执行位，开发时直接用 Bash 调用。

- `bash md.sh check`：运行主工具的检查流程。
- `bash deploy.sh`：将脚本和依赖包部署到配置好的远端主机。
- `bash ssh.sh`：配置局域网或公网环境下的 SSH 免密访问。
- `bash -n md.sh deploy.sh ssh.sh`：提交前必须执行的语法检查。

如果本机安装了 `shellcheck`，提交前额外执行 `shellcheck *.sh`。

## 编码风格与命名约定
统一使用 Bash，不要退回 POSIX `sh`。保持现有风格：函数和控制块内使用 4 空格缩进；常量和配置项使用全大写命名，如 `REMOTE_HOST`、`KEY_PATH`；短生命周期局部变量使用小写命名，如 `port`、`status`。在 `md.sh` 中，命令处理函数保持 `module::action` 形式，并继续复用 `log_info`、`log_ok`、`log_warn`、`log_err` 输出用户提示。变量展开要加引号，列表优先使用数组，不要手写空格分隔字符串。

## 测试指南
仓库目前没有自动化测试套件。最低要求是对所有改动脚本执行 `bash -n`，并手动跑一遍受影响的命令路径。涉及 SSH、挂载、`sudo` 或部署流程的改动，先在非生产环境验证，并在 PR 中写明实际执行过的命令。

## 提交与 Pull Request 规范
最近提交历史使用带方括号的前缀风格，例如 `[FEAT][witt]...`、`[FIX][witt]...`、`[REFACTOR][witt]...`。继续采用该格式：`[TYPE][scope]简短摘要`，其中 `TYPE` 保持大写，摘要尽量简洁。PR 需要说明修改了哪个脚本、影响的目标环境、执行过哪些验证命令，以及是否引入了新的交互提示或副作用。只有当终端交互流程明显变化时，才需要附截图。
